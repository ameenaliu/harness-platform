## Mechanics — OpenAI Codex

- **No plugin**: Codex never installs the `platform-sdlc-harness` plugin. It reads the committed `AGENTS.md` (the universal hub) + the copied conventions under `.agents/skills/*-conventions/SKILL.md`. This role is a subagent at `.codex/agents/<name>.toml` (`name`, `description`, `developer_instructions`; optional `model`, `sandbox_mode`). The orchestration that ties the roles together lives in the `platform-dev-workflow` skill (`.agents/skills/platform-dev-workflow/SKILL.md`).
- **GitHub mechanism**: Codex runs the **`gh` CLI** via shell — `gh issue`, `gh pr`, `gh project`, `gh api`, `gh api graphql`. There is **no MCP server** — the agent TOMLs declare no MCP servers at all. `gh` must be installed and authenticated in the Codex environment (scopes `repo`, `project`, `read:org`) before the workflow runs — verify with `gh auth status` at the start of Phase 1 and stop with a clear message if it is not authed. Org / repo / project number / branch names come from `.claude/context/platform-context.md`; never hardcode them.
- **Delegation**: Codex spawns subagents **only when explicitly told to**. The workflow skill instructs the parent, at each phase, to "spawn the `<role>` subagent for this task". The repo is a single monorepo so all work is sequential — no parallel spawning across repos. The parent thread orchestrates; child threads do bounded work; the parent reconciles.
- **Isolation**: each spawned subagent runs in its own thread. Commit on the **user branch** directly with Conventional Commits (`<type>(<surface>): <description>`) — one commit per atomic change is fine, no need to squash to one per task. Git worktrees are optional in Codex (only worth it for parallelism the workflow doesn't need).
- **Read-only reviewer (Phases 3, 4, 6, 7)**: `reviewer.toml` sets `sandbox_mode = "read-only"`.
- **Phase 10 reviewer mode**: when the parent spawns the reviewer for Phase 10 PR review, it must run with shell/network access so the reviewer can post comments via `gh` (`gh api repos/{owner}/{repo}/pulls/<n>/comments` for inline findings + `gh pr review <n> --comment` for the summary). The reviewer still never edits source files — its only writes are the PR comments via `gh`.
- **Gates**: the workflow skill instructs the parent to **STOP at each of the 3 human gates (GATE #1 after planning, GATE #2 after Phase 4 pre-test review, GATE #3 before PR creation)** and ask the human for `APPROVED` before spawning the next phase's subagents. Do not auto-advance past a gate.
- **Holistic phases (4, 7, 10)**: these are reviewer-only and informational — even on CRITICAL findings, the verdict is `INFORMATIONAL` and the workflow continues to the next gate where the human decides.
- **Status contract**: each subagent ends with the `📋 AGENT STATUS` block; the parent parses it to decide the next action.
